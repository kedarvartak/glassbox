# 21 · Context Cleaner — Design & Execution Plan

> **What this doc is:** The full design for Glassbox's cleaner layer — what it does, what it does NOT do, the execution model, and the phased build plan. Builds directly on the detection taxonomy ([doc 20](./20-context-garbage-evidence-and-taxonomy.md)) and the reclaimable analyzer already implemented in `packages/analysis`.

---

## 1. The core question: what does "clean" mean here?

Detection answers: *"which segments are garbage?"*
The cleaner answers: *"what do we do about it?"*

These are different problems. Detection is a read-only, deterministic analysis over a normalized model. Cleaning requires **making decisions** (is this safe to remove?), **producing artifacts** (something the agent or user acts on), and **respecting a hard constraint** — Glassbox does not modify session transcripts or live agent state. It is, and must remain, **read-only on its data sources**.

This constraint is not cosmetic. It is:
- A trust guarantee to users ("Glassbox never touches your sessions")
- A safety guarantee (no risk of corrupting a live session)
- An architectural simplicity guarantee (the cleaner is stateless over sessions)

The cleaner therefore does not *delete* garbage. It **prescribes the minimal interventions** that let the agent or user eliminate it, and where it can act independently (Claude.md injection, `compact` triggering via the CLI) it does so with explicit user confirmation.

## 2. What the cleaner does — the three output types

### 2.1 Prescription report (always produced, read-only)
A structured, prioritized list of *what to clean and why*, grouped by type and sortable by token savings. This is the output most users see first — it's the "reclaimable report" from the analyzer extended with actionable recommendations.

**Format:** rendered in the UI as a hygiene panel; also emittable as JSON from the CLI.

**Contents:**
- Segment-level verdict (gone / stale / spent / duplicate) with reason and token count
- Grouped by intervention type (see §3)
- Total reclaimable tokens + estimated USD saved per turn if cleaned
- Confidence level per finding (provable / heuristic)

### 2.2 CLAUDE.md injection (user-confirmed, write operation)
For the category of *stale memory* and *orphaned file references*, the most effective clean is updating CLAUDE.md to tell Claude which files/paths to stop referencing. This is a supported, idiomatic Claude Code pattern — it's the memory write the agent itself would make.

**The cleaner generates the specific CLAUDE.md block to inject** — the user reviews it and confirms before any file is touched.

**Example output:**
```markdown
## Context hygiene — [generated by Glassbox, 2026-06-06]
The following files were deleted or significantly changed since they were last
read into context. Do not reference or re-read them in this session:
- src/old-auth.ts (deleted 2026-06-05)
- docs/old-spec.md (overwritten 3× — earlier copies are stale)
```

### 2.3 Compact trigger (user-confirmed, CLI action)
Claude Code exposes a `compact` mechanism that summarizes and resets the context window. The cleaner can:
1. **Detect** when the reclaimable percentage exceeds a configurable threshold
2. **Recommend** a compact with a suggested focus summary (what to preserve)
3. **Optionally trigger** it via the Claude Code API/CLI with user confirmation

This is the most aggressive action — it nukes the whole window — so it requires explicit opt-in and only fires when the reclaimable% is high enough to justify the disruption.

## 3. Intervention taxonomy (mapping garbage types to clean actions)

| Garbage type | Detection signal | Cleaner action | Confidence |
|---|---|---|---|
| **gone** (deleted file) | `modifiedAt → null` | CLAUDE.md injection: "stop referencing X" | High — provable |
| **stale (disk-drift)** | `modifiedAt > capturedMs + 3s` | CLAUDE.md injection: "re-read X, your copy is outdated" | High — provable |
| **stale (superseded)** | Later read of same path in-session | No action needed — agent already has the newer copy | N/A |
| **spent** (one-shot tool) | Tool in ONE_SHOT_TOOLS, not in last turn | Compact recommendation (threshold-gated) | Heuristic |
| **spent** (MCP) | `source === "mcp"`, not in last turn | Compact recommendation (threshold-gated) | Heuristic |
| **duplicate** | Same content hash, multiple copies | Compact recommendation (threshold-gated) | High |

Key design decision: **CLAUDE.md injections handle file-specific garbage**; **compact recommendations handle accumulated non-file garbage** (spent tool outputs, MCP envelopes, duplicates). These are complementary, not competing strategies.

---

## 4. What the cleaner does NOT do

It is important to be precise about scope:

- **Does not modify session JSONL files.** Never. Read-only.
- **Does not inject into a live running agent process.** No in-process patching.
- **Does not auto-run without user confirmation.** Every write-side action is gated.
- **Does not clean the superseded-in-session stale type.** The agent already has the newer copy; the old copy is flagged by detection but there is no useful intervention (you cannot retroactively remove earlier messages from the window).
- **Does not interpret semantic content.** The cleaner makes no judgements about whether a spent output "might still be needed" — it applies the detection verdicts as-is. The confidence rating tells the user how much to trust the verdict.
- **Does not cross session boundaries.** One session = one cleaning context.

## 5. Execution model (the algorithm)

```
analyzeSessionReclaimable(session, { repo, tokens })
        │
        ▼
  ReclaimableReport
  (segments + verdicts + token counts)
        │
        ├──► plan(report, session, opts) ──► CleanPlan
        │         │
        │         ├── claudeMdBlocks: CleanAction[]   (file-level)
        │         ├── compactRecommendation?: CompactHint   (threshold-gated)
        │         └── summary: { reclaimableTokens, topItems, estimatedUsdSaved }
        │
        ├──► applyClaudeMd(plan, projectPath)   [write, user-confirmed]
        │
        └──► triggerCompact(plan, session)      [CLI, user-confirmed]
```

### 5.1 `plan()` — the core cleaner function

Input: `ReclaimableReport` + `Session` + `CleanOptions`
Output: `CleanPlan`

```typescript
interface CleanPlan {
  // CLAUDE.md blocks to inject (one per affected file path).
  readonly claudeMdBlocks: CleanAction[];
  // Compact recommendation, present only when reclaimable% > threshold.
  readonly compactRecommendation?: CompactHint;
  // Human-readable summary for the UI.
  readonly summary: CleanSummary;
}

interface CleanAction {
  readonly type: "stop_referencing" | "re_read";
  readonly path: string;
  readonly reason: string;         // one-line shown to user before they confirm
  readonly reclaimableTokens: number;
  readonly claudeMdSnippet: string; // the exact text to inject
}

interface CompactHint {
  readonly reclaimablePct: number;
  readonly reclaimableTokens: number;
  // Suggested /compact focus prompt — what to ask Claude to preserve.
  readonly suggestedSummaryFocus: string;
  readonly estimatedUsdSaved: number | null;
}
```

**Planning rules:**
1. For each `gone` segment: emit a `stop_referencing` action for its path.
2. For each `stale (disk-drift)` segment: emit a `re_read` action for its path.
3. Deduplicate by path — one action per path, not one per segment.
4. If `reclaimablePct > opts.compactThreshold` (default: 0.25): emit a `compactRecommendation` with a `suggestedSummaryFocus` built from the session's last user message + last assistant reply text.
5. Sort `claudeMdBlocks` descending by `reclaimableTokens` (biggest wins first).

### 5.2 `applyClaudeMd()` — the file writer

Reads the existing CLAUDE.md at `projectPath`, appends a timestamped Glassbox block, and writes it back. No other files are touched. Uses a section marker so repeat runs are idempotent (replace the existing block, don't append duplicates).

```
<!-- glassbox:start -->
## Context hygiene — Glassbox 2026-06-06T12:00Z
...generated content...
<!-- glassbox:end -->
```

### 5.3 `triggerCompact()` — the compact invoker

Calls `claude --compact` (or the equivalent API) with the `suggestedSummaryFocus` as the focus parameter. User confirmation required at the CLI layer before this is called.

## 6. Confidence and honesty

The cleaner labels every action with a confidence level:

| Level | Meaning | Actions that use it |
|---|---|---|
| `provable` | Deterministic from the model + filesystem. The claim is true by definition. | gone (file deleted), disk-drift stale |
| `heuristic` | Based on the ONE_SHOT_TOOLS list or MCP source tag — correct for the common case but may be wrong for atypical usage. | spent tool output, spent MCP |
| `session-inferred` | Superseded-in-session: provable from the model, but the earlier copy can't be cleaned anyway. | superseded stale (informational only) |

The UI renders confidence as a subtle label. Heuristic-confidence items include a one-line note: *"This is a judgment call based on tool name — override if you know this output is still needed."*

## 7. Build plan (phased)

### Phase A — Plan generation (analysis layer, no UI, no writes)

**Scope:** implement `plan()` in `packages/analysis/src/cleaner.ts`. This is pure business logic over the existing `ReclaimableReport` — no filesystem writes, no CLI, just data transformation.

**Deliverables:**
- `packages/analysis/src/cleaner.ts` — `plan()`, `CleanPlan`, `CleanAction`, `CompactHint` types
- `packages/analysis/src/cleaner.test.ts` — unit tests for all planning rules:
  - gone → stop_referencing action
  - disk-drift stale → re_read action
  - deduplication by path
  - compact threshold: below → no CompactHint; above → CompactHint with correct focus
  - sort order (tokens descending)
- Export from `packages/analysis/src/index.ts`

**DoD:** all unit tests pass; `plan()` is callable from the CLI layer.

### Phase B — CLI integration (read-only, no writes)

**Scope:** add a `glassbox clean --dry-run <session>` command in `packages/cli` that prints the `CleanPlan` in human-readable form. No files written. User can see exactly what actions would be taken.

**Deliverables:**
- `glassbox clean --dry-run` — renders plan as a formatted table: action type, path, reason, tokens saved, confidence
- `glassbox clean --json` — emits `CleanPlan` as raw JSON for piping

**DoD:** dry-run command works on a real session; output is readable and accurate.

### Phase C — CLAUDE.md write (user-confirmed write)

**Scope:** implement `applyClaudeMd()` and add `glassbox clean --apply` to the CLI. Requires explicit `--yes` flag or interactive confirmation prompt — never writes silently.

**Deliverables:**
- `packages/analysis/src/cleaner.ts` — `applyClaudeMd()` with idempotent section marker
- `glassbox clean --apply` — shows plan, prompts for confirmation, writes CLAUDE.md
- Tests for idempotency (running twice produces the same CLAUDE.md, not doubled content)

**DoD:** writes correct CLAUDE.md on a test project; re-running is idempotent; user confirmation is always required.

### Phase D — Compact trigger (user-confirmed CLI action)

**Scope:** implement `triggerCompact()` and `glassbox clean --compact`. This is the most invasive action so it's last and most guarded.

**Deliverables:**
- `glassbox clean --compact` — shows reclaimable% + suggested focus, requires `--yes` or interactive confirm, then triggers compact
- Threshold configuration (CLI flag + optional `glassbox.config.ts`)

**DoD:** compact trigger works end-to-end; threshold default (25%) tested; user always confirms.

### Phase E — UI hygiene panel

**Scope:** surface the `CleanPlan` in the Glassbox UI as a hygiene panel in the SessionView — a prioritized list of recommendations with one-click "Apply" for CLAUDE.md actions.

**Deliverables:**
- `HygienePanel` component in `packages/ui`
- Shows: reclaimable%, items sorted by token savings, per-item action button
- "Apply CLAUDE.md changes" triggers the CLI action (or calls the analysis API if running server-mode)
- Compact recommendation shown as a distinct call-to-action card when threshold exceeded

**DoD:** hygiene panel renders correctly on a real session; actions reflect actual plan output.

## 8. Key design decisions (and the reasoning)

### Why CLAUDE.md injection instead of direct context manipulation?
Claude Code's memory model treats CLAUDE.md as authoritative instructions. Injecting a "don't reference these paths" block is *safer and more durable* than any in-process patch — it survives context compaction, session restarts, and doesn't require any API the agent doesn't already expose. It's also the action the agent would take itself if it knew about the garbage.

### Why threshold-gate the compact recommendation?
A compact resets the entire window — it's a nuclear option. Recommending it for a 3% reclaimable rate would be noise and erode user trust. 25% is the default floor: above that, the accumulated garbage is significant enough that the disruption of a compact is justified by the savings.

### Why separate Phase A (planning) from Phase C (writing)?
The plan is independently useful: it can feed the UI, the dry-run, JSON export, and future integrations without the write capability. Keeping them separate means the cleaner's intelligence is testable without file I/O, and users can inspect before acting.

### Why no auto-clean mode?
Context windows contain semantic state the model depends on. Auto-cleaning without review risks removing something the agent was still using (especially for heuristic-confidence verdicts). Trust is built incrementally: show the report → dry-run → user-confirmed apply → then (maybe, much later) auto mode for explicit opt-in power users.

## 9. Relation to the broader product roadmap

This cleaner represents the **"Advise" tier** from doc 20's product-modes ladder:

> Observe (reclaimable report) → **Advise (what to clear)** → Act (MCP proxy / session optimizer)

The full "Act" tier — an MCP proxy that strips garbage *before* it enters context — is a later, infrastructure-grade feature that requires either MCP instrumentation or SDK-level integration. The cleaner described here is the **bridge between observation and action** that delivers real value now, without requiring infrastructure changes.

## 10. Success criteria for the cleaner

| Criterion | Target |
|---|---|
| Plan accuracy | No false-positive "stop_referencing" actions (provable-confidence only for CLAUDE.md writes) |
| Idempotency | Running `--apply` twice produces identical CLAUDE.md |
| User trust | User always sees the plan before any write occurs |
| Token savings in practice | ≥ 20% reclaimable in a representative session (dogfooded on real sessions) |
| CLI round-trip | `clean --dry-run` completes in < 1 s on a 10k-message session |
